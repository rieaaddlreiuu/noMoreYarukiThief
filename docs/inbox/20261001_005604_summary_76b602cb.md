# セッション要約: ユーザーごとの通知チャンネル（`/niki notify`）

## 背景・経緯

- [docs/extension.md](../extension.md) の「5. ユーザーごとに通知チャンネルを変更できるようにする」を実装するセッション。
- 現状は、Bot の通知（宣言・取消・結果）がサーバーごとに1つの「既定チャンネル」へ集中し、メンバーが増えると流れが追いにくかった。
- 最初は「個人チャンネルへ差し替える」案（案A）で実装した。
- その後、次の2点の要望が出たため、方針を変更した。
  1. 個人チャンネルだけでなく、**サーバー既定チャンネルにも必ず複製投稿する**（案B）。
  2. チャンネルを引数で指定するのではなく、**`/niki notify` を実行したチャンネルをそのまま通知先にする**。
- 途中で、最初のマイグレーション（`202610010001`）を Supabase に**実行済み**と分かった。そのため既存ファイルは編集せず、差分を新規ファイルで足す形にした。

## 開発者に説明したこと・理解してもらったこと

- **変更内容**: どのファイルをどう変えたか、ファイルごとの全体の役割。
- **`/niki notify` の処理の流れ**:
  1. Discord から Bot に届く。
  2. 署名を検証し、3秒以内に「考え中」と返す（Discord の3秒ルール）。
  3. 実処理を後から行い、結果で元の応答を書き換える。
- **権限の確認**: 次の順に確認する。
  1. 署名検証。
  2. サーバー内で実行されたか。
  3. `/niki setup` 済みか。
  4. GitHub 連携済みか。
  5. Bot の投稿権限（`assertChannel`）。
  - 管理者権限は不要。対象は本人の分だけで、他人や他サーバーの設定は変えられない。
- **複製投稿の仕組み**:
  - 通知を「チャンネルごとに1行」に増やした（通知の予約表のようなテーブル）。
  - 既定チャンネルへの投稿が先、個人チャンネルが後。
  - 個人チャンネルへの投稿が失敗しても、既定チャンネルの投稿は止まらない。
  - 個人チャンネルが既定と同じ場合は1件だけ。
- **宛先の固定**: 通知の宛先は「通知を作った時点」で固定される。設定を後から変えても、作成済みの通知は変わらない。

## 決定事項

- 通知は**案B（既定に必ず複製投稿）**。公開性が保たれるため、「非公開チャンネルを弾く」対応は不要になった。
- `/niki notify` は、実行したチャンネルを個人の追加通知先にする。解除は `reset:true` オプション。
- チャンネルIDは、署名済みのペイロードの `channel_id` を使う。ユーザーが任意のIDを指定することはできない。
- 適用済みの `202610010001` は編集せず、差分は `202610020001` として新規追加した。
- 適用済みの `202610010001` で個人設定をした人は、その設定が引き継がれる。次に `/niki notify` を実行するまで、既定に加えて個人チャンネルにも投稿される。
- 配信のコード（jobs.ts / client.ts / messages.ts）は変更しない。通知1行ごとに完結する作りのため。
