# 絶対に開発させるニキ:壁打ちまとめ

技育プロジェクト(サポーターズ)向け。2週間・3人。作るものは Discord Bot。

## 1. 前提

- 対象イベント:技育プロジェクト(サポーターズ)。技育展2026のエントリー期間は 2026/9/9〜10/12。ただし今回の「2週間」がどのイベントの枠かは**未確認**。
- 期間2週間、3人、ユーザーが開くのは Discord のみ。
- Webアプリは必須ではないとの確認済み。ただし応募要件・審査基準は公式ページで要確認。

## 2. コンセプト

課題:開発がめんどくさくなる学生エンジニアが、着手できない・続かない・詰まって放置する。

> 宣言する → 仲間に見える → GitHubで自動確認 → ニキが称える/煽る

- 対象は学生エンジニア(チームで使う想定)。
- 通知先は Discord。仲間の目がある状態が圧力になる。
- 一人用も検討したが、チーム用で進めることに決定。

## 3. MVP機能

1. `/setup`:通知チャンネルの設定(管理者のみ)
2. `/link`:GitHub アカウントの紐付け
3. `/declare`:開発の宣言(内容・リポジトリ・期限)
4. 期限後の自動判定(GitHub のコミット有無)
5. 結果通知(達成→称賛、未達成→煽り。最初は固定テンプレート)
6. `/status`:チームの達成状況、連続日数、達成率

### 拡張(2週目、余力次第)

- LLM による状況連動の煽り文
- 煽りの強度選択(優しい/普通/鬼)
- 週次サマリー
- 宣言前リマインド

### 対象外

- 独立した Web ダッシュボード
- スマホアプリ
- GitHub 以外の Git サービス
- 複雑なポイント・報酬設計

## 4. 技術選定(たたき台)

| 領域 | 選定 | 理由 |
|---|---|---|
| 言語 | TypeScript | 全体で統一 |
| Bot ライブラリ | discord.js | 情報が多い |
| DB | Postgres(Supabase / Neon) | 連続日数・達成率を SQL で集計しやすい |
| ORM | Prisma または Drizzle | 型安全 |
| GitHub 連携 | Octokit | コミット取得 |
| 定期実行 | node-cron(Bot プロセス内) | 追加サービス不要 |
| ホスティング | 常駐できるサービス(Railway / Fly.io / Render 等) | 料金・無料枠は要確認 |
| 生成AI(拡張) | LLM API | 煽り文の生成 |

### Bot の動かし方の分かれ道

| | A:Gateway 常駐型 | B:HTTP Interactions 型 |
|---|---|---|
| 仕組み | Bot が常時接続 | コマンド受信時だけ URL が呼ばれる |
| 利点 | 情報が多く実装が楽 | 常駐サーバー不要(Vercel 等) |
| 弱点 | 常駐ホスティングが必要 | 署名検証・3秒制限への対応、外部 cron が必要 |

上記の技術選定は A を前提にした案。

### 【要すり合わせ】チームの READ.md との差分

チームが作成した「開発促進Discord Bot:MVPまとめ」(READ.md)は、次の構成を採っている。

- Next.js(Route Handlers)+ Vercel
- Supabase PostgreSQL + `@supabase/supabase-js`
- Supabase Cron で5〜10分おきに判定 API を呼ぶ
- HTTP Interactions + Discord REST API(常駐 Gateway Bot は採用しない)
- GitHub OAuth App で Discord と GitHub を紐付け
- Octokit、Zod、`discord-interactions`(署名検証)

つまり本まとめの「A:Gateway 常駐 + node-cron」案とは方針が異なる。READ.md の案は常駐サーバーが不要で、GitHub OAuth による本人確認もある一方、署名検証や3秒制限への対応が必要になる。**どちらで進めるかをチームで決め、片方に統一する**こと。READ.md の仕様(1サーバー=1チーム、公開リポジトリのみ、API エラーを未達成にしない、通知状態の分離など)は、どちらの方式でも活かせる。

## 5. Discord Bot の権限

### 招待時

- スコープ:`bot`、`applications.commands`
- Bot 権限(最小):チャンネルを表示、メッセージを送る、リンクを埋め込み → Permissions Integer `19456`
- 付けない:管理者、全員宛にメンション、管理系の権限
- ファイル添付が必要になったら「ファイルを添付」を追加(グラフ画像など)

### Gateway Intents

- 有効にするのは `Guilds` のみ。
- Message Content / Server Members / Presence の特権インテントは使わない。
- メンションは `<@ユーザーID>` 形式で送れる。

### コマンドの実行権限

- `/setup`:サーバー管理者のみ(`default_member_permissions` に「サーバー管理」+処理内でも確認)
- `/declare`、`/status`、`/link`:全員。ただし対象は自分のデータのみ
- 設定系の返信は ephemeral(本人にだけ表示)、公開するのは通知のみ

### プライバシー・秘密情報

- 保存する項目(Discord ID、サーバー ID、GitHub ユーザー名、宣言内容と結果)を明示する。
- DB の検索は必ずサーバー ID で絞る。
- 未達成が名指しで通知されることを、初回に案内する。
- Bot トークン等は環境変数で管理し、リポジトリに含めない。誤ってコミットしたらすぐ再発行。
- 開発用と本番用で Bot(アプリ)を分ける。

### GitHub 側

- MVP はパブリックリポジトリのみ。
- 自己申告(ユーザー名入力)は他人の名前を入れられる。OAuth なら本人確認ができる(READ.md は OAuth 案)。
- プライベート対応は GitHub App(Contents / Metadata の read-only)などを検討。

## 7. 役割分担(機能ごと・縦割り)

| 担当 | 範囲 |
|---|---|
| A:基盤・設定 | 雛形、DB 設計、デプロイ、`/setup`、`/link`(OAuth にする場合は受け皿も) |
| B:宣言・検知(最難関) | `/declare`(モーダル)、定期実行、Octokit での検知と判定 |
| C:通知・体験 | ニキの文面、通知 Embed/ボタン、`/status`、週次サマリー、LLM 文面 |

- 共通:1日目にデータ構造・ブランチ運用を合意。13日目以降は全員でデモ動画と発表資料。
- 依存の対策:ダミーデータで先に作り、あとでつなぐ。8日目に結合。
- B に負荷が集中しやすい。遅れたら A が定期実行の一部を引き取る。

## 8. スケジュール案(2週間)

- 1〜3日目:企画確定、データ構造合意、GitHub・Discord 連携の技術検証(B の検知検証が最優先)
- 4〜8日目:MVP 実装。8日目に結合し、宣言→判定→通知の一周を動かす
- 9〜12日目:拡張機能、UI 磨き込み、自分たちで運用して実績を取る
- 13〜14日目:デモ動画、発表資料、バグ修正

## 9. リスクと対策

- GitHub コミット取得の反映遅延 → 期限直後でなく数分の猶予を持って判定
- API 障害を未達成にしない(確認エラーとして再試行)
- 定期処理の重複で同じ結果を繰り返し投稿しない
- 時刻:入力は JST、DB は UTC で統一
- Bot が落ちる → 期限は DB に保存し、再起動後に未処理分を拾う
- 煽りが不快にならない配慮(強度選択、初回の案内)
- 「本当に効果があるか」を問われる → 自分たちの運用実績(宣言・コミット・通知・集計)で示す

4. 検知対象:特定リポジトリか、ユーザーの全コミットか(READ.md は宣言時に指定)

7. 通知チャンネル:管理者が指定するか、Bot が専用チャンネルを作るか(後者は権限が広がる)
8. 対象イベントの応募要件・締切・審査基準の確認
