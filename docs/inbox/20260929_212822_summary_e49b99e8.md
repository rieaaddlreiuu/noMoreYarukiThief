# セッション要約: アーキテクチャ解説の作成とAI拡張案の検討

## 背景・経緯

開発者（非エンジニア）から、このリポジトリ（「開発ニキ」— Discordで開発の宣言・達成判定を行うbot）について、以下の流れで質問・依頼があった。

1. まず「Discord botの通信の仕組み」「botはどうやってアプリのURLを読んでいるのか」「アプリにbotの情報を入れるだけで通信できるのか疑問」という質問があり、Discordの**Interactions（Webhook）方式**（Discordのサーバー側からアプリへHTTP POSTしてくる仕組みであり、アプリが能動的に接続しに行くのではないこと）を説明した。
2. 続けて「サーバーの構成全体を、教科書レベルで・図表を使って・外部インフラも含めて」説明してほしいという依頼があり、`docs/architecture.md`を新規作成した。
3. さらに「サーバーの構成（使っているモジュール）」「Next.js初心者がAIを使わず一から組むなら」という観点の追記依頼、および「APIサーバーの構成・TypeScriptでの書き方」の追記依頼があり、同じファイルに章を追加した。
4. 判定ロジックについての質問（「目標が達成されたかどうかどう判断しているか」）に回答した後、「Gemini APIなどを使って“コミットしたか”ではなく“目標に沿ったコミットをしたか”を判定できないか」という提案があり、実現可能性を説明。
5. 4を実装する計画をPlan Modeで検討したが、ユーザーはその場でのExitPlanMode（実装着手）を却下し、代わりに「チーム開発でPRをマージした場合の扱いはどうなるか」という別の質問をした → Merge commit / Squash / Rebase それぞれでの判定への影響（特にSquash/Rebase時の日時ずれ・共著者非認識の問題）を説明した。
6. その流れで、4つの拡張機能（AI判定・Co-authored-byパース・あおりメッセージ生成・定期コントリビューション表示）の仕様案を`docs/extension.md`にまとめるよう依頼された。
7. 最後に、5つ目の拡張（ユーザーごとに通知チャンネルを変更できるようにする）の追加依頼と、2番目の拡張（Co-authored-byパース）を「ひとまず中止」にする指示があった。

**注記**: このセッションでは**コードの変更は一切行っていない**。すべてドキュメント（`docs/architecture.md`、`docs/extension.md`）への説明・設計メモの追記のみ。

## 開発者に説明したこと・理解してもらったこと

### Discordとの通信の仕組み
- Discordは「Interactions Webhook」方式（Discordのサーバーがアプリの公開URLへ直接POSTしてくる）を採用しており、Gateway方式（常時接続）ではない
- 通信が成立するには「Discord Developer Portal側にアプリのURLを登録すること」と「アプリ側にBotトークン・公開鍵を設定すること」の**両方**が必要（片方だけでは繋がらない）
- `DISCORD_PUBLIC_KEY`（受信検証用・公開してよい）と`DISCORD_BOT_TOKEN`（送信認証用・厳重に秘密）の役割の違い
- 3秒以内応答ルールと、`after()`を使った「先に仮応答→後で本処理→返信を編集」という2段階応答の仕組み

### 全体アーキテクチャ（`docs/architecture.md`に記載）
- Vercel（アプリ本体・サーバーレス）、Discord（対話窓口）、GitHub（本人確認・コミット確認）、Supabase（DB+Cron）の4サービスが連携し、**アプリがハブとなり、他サービス同士は直接会話しない**という全体構造
- GitHub OAuth連携はブラウザ経由のリダイレクト型（PKCE・state・HttpOnly Cookieで保護）であり、Discord Webhook型とは通信の向きが根本的に異なる（そのためGitHub連携だけはlocalhostのままngrok無しでテストできる）
- SupabaseのRLS（Row Level Security）を「ポリシーなしで全拒否＋service_roleのみ許可」という設計にしていること
- Supabase Cronが「サーバーレスにはタイマーがない」問題を解決する定期実行の仕組みであること

### サーバー構成・モジュール・APIの書き方（`docs/architecture.md`に追記）
- 使用モジュール一覧（next, zod, discord-interactions, @octokit/rest, @supabase/supabase-js, server-onlyなど）とその役割、および「モジュールなしで自作する場合何が必要か」の対比
- App Routerの「ファイルパス＝URL、関数名＝HTTPメソッド」という基本ルール
- Next.js初心者がAIなしで一から組む場合の14段階の学習順序（「動く→正しくする→安全にする」の3段階を意識する）
- Route Handlerの書き方（`Request`/`Response`の読み書き、`NextResponse`、`runtime`/`maxDuration`設定、エラーハンドリングの型、zodによる実行時バリデーション）

### 目標達成の判定ロジック
- `matchesDeclaration`（`src/lib/github.ts`）は「①コミットのauthor.idが宣言者本人のGitHub IDと一致」「②コミット日時が宣言登録〜期限の範囲内」の両方を満たすコミットが1件でもあれば「達成」とする
- 「未達成」と「確認エラー」を明確に区別しており、GitHub側の取得失敗（レート制限・404など）は未達成にせず自動リトライすること
- **チーム開発のPRマージ時の注意点**:
  - Merge commit戦略なら個々のコミットの作者・日時がそのまま保持され問題なし
  - Squash/Rebase戦略だと、日時が「マージ実行時刻」に書き換わるため、期限内に書いたコードでもレビュー待ちで期限後にマージされると誤って未達成になりうる
  - Squashされたコミットは構造化された`author`フィールドに1人分しか情報が残らず、`Co-authored-by:`で記録される共著者は現状カウントされない

## 決定事項

1. **AIによるコミット内容判定（Gemini API）を追加する方針で設計を進める**。判定材料は**コミットメッセージのみ**（diffは見ない）、**`GEMINI_API_KEY`が設定されている場合だけ有効化**し未設定なら従来通りの動作にフォールバックする、という2点をユーザーが選択・確定した。
2. **Co-authored-byパース機能（拡張案2）は、ひとまず中止（保留）**。なりすましリスク（他人のGitHub IDを勝手に`Co-authored-by:`に書ける）が明確な懸念として残っており、着手は見送り。設計メモは参考用に残してある。
3. **拡張案5「ユーザーごとの通知チャンネル設定」を新規追加**。ただし「チーム全体に公開して社会的圧力をかける」という現在の設計思想との間にトレードオフがあり、「完全に個人チャンネルへ差し替える」か「既定チャンネルへの複製投稿も残す」かは、今後プロダクト方針として判断が必要な**未決事項**として明記した。
