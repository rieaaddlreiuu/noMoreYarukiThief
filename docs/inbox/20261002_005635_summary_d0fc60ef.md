# セッション要約: 定期実行（ステータス変更）の仕組みの解説

## 背景・経緯
- 開発者から「定期的に実行するステータス変更の処理の流れを、初めて見る人でもわかるように、コード単位で説明してほしい」と依頼があった。
- 参照資料は `docs/architecture.md`（全体構成の説明）。ただし6章は図だけで、コードレベルの説明が不足していた。
- 実際のコード（下記）を読んで説明を作成した。コードの変更はしていない。

## 開発者に説明したこと・理解してもらったこと
定期実行は「Supabase Cron が5分おきにアプリを起こす → アプリが判定対象を1件ずつ処理する」流れ。

1. **きっかけ**: `supabase/cron.sql` の pg_cron（PostgreSQLの定期実行機能）が5分おきに `/api/jobs/evaluate` へHTTP POST。合言葉（`CRON_SECRET`）をBearerトークンで付ける。
2. **入口**: `src/app/api/jobs/evaluate/route.ts` が合言葉を照合 → 掃除（cleanup） → `runJobs` を起動。
3. **ループ本体**: `src/lib/jobs.ts` の `runJobs`。持ち時間40秒（Vercelの上限60秒より短く）で、「判定1件 → 通知1件」を最大10ラウンド。
4. **判定対象の選び方**: SQL関数 `niki_claim_check`。`status='pending'` かつ `next_check_at` が来ているものを1件だけ取り、2分間の「予約（lease）」を付ける。二重処理防止と、落ちた処理の引き継ぎのため。
5. **GitHubでの判定**: `src/lib/github.ts` の `findQualifyingCommit`。公開リポジトリか確認 → ブランチ取得 → 宣言〜期限の間の本人コミットを最大20ページ探す → （Gemini設定があれば）AIで宣言内容に合うか判定。ユーザー本人の暗号化トークンを優先し、無効なら運営トークンにフォールバック。
6. **ステータス更新**: SQL関数 `niki_finish_check`（最新は `202610040001_early_check.sql`）が唯一の更新箇所。
   - コミット発見 → `succeeded`（期限前でも）＋通知を作成
   - 未発見かつ期限前 → `pending` のまま次回確認時刻を設定（残り1時間超は30分後、以内は10分後）
   - 未発見かつ期限後 → `failed` ＋通知を作成
7. **エラー時**: `niki_retry_check` で待ち時間を延ばして再試行（1分から倍々、上限1時間）。期限前は再試行が期限を越えないようにしている。
8. **通知**: ステータス変更で `notifications` に行が増え、同じループ内で Discord に投稿。
9. **ポイント**: 「Cronが5分おき」≠「各宣言を5分おきに確認」。Cronは起こす役で、実際の確認は `next_check_at` が来た宣言だけ。

補足: SQL関数は migration で何度も上書きされており、番号が最も新しいものが有効。
